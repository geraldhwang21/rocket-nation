Database architecture and sources

Current release: v21 retains only California, New York and Texas. All 208 rows tagged to other states were removed from the calling list, browser data and downloadable workbook. Historical collection and merge descriptions below remain the record of how the earlier list was built.

Contents

Version 21 is a SQLite calling_list table with 72,270 company records and nine public fields: phone, name, trade, address, city, website, email, website_source, and status. The same rows appear in CSV, Excel, and three website data files. Read-only checks confirm 10,981 recorded websites, 4,264 email rows, 2,046 raw trade labels, and 475 city labels. Of these, 8,772 rows have “found” website status. These are source and website-verification labels, not proof of current operation, commercial suitability, or permission to contact.

Construction and sources

The frozen v17 v3 list supplied 72,405 phone-keyed rows. Its v18 successor used Overture records, Serper searches, and Haiku 5.5 model searches. Version 19 continued from that exact successor: one coordinator submitted 9,830 distinct eligible phones through Anthropic Message Batches and added 1,209 accepted websites and 829 emails while preserving existing nonblank values. Version 20 reconciled a separate 100-record research set using reviewed identity rules: 27 matched existing companies and 73 became new rows. Seven matched companies gained previously blank websites. Research websites entered as “needs_review”; two conflicting existing website values were retained.

Validation

For the v19 additions, model answers were candidates. Page-verification code rejected directory, social, and private-network destinations and required fetched content showing the phone plus company-name/domain evidence. A recorded network-disabled replay checked the 1,209 accepted website decisions against retained inputs. That proof does not cover every inherited website or the v20 research additions. Recorded checks bind inputs and outputs by SHA-256, test database integrity, compare database/CSV/Excel/browser rows, and check preservation of prior nonblank values. Frozen inputs and scripts support rebuilding v19 and v20 without repeating searches. Complete pre-v17 reconstruction is unavailable.

Process and agents

Codex and Claude sessions coordinated research, implementation, review, and reconciliation; Haiku 5.5 low-effort requests supplied search candidates through the Batch API. The v19 run used one-item and three-item gates before 30 disjoint queue partitions—not 30 proven simultaneous agents. Its controller recorded intent, acceptance, results, and usage to prevent new duplicate submissions. The v18 report records 66 earlier duplicate submissions; the v19 report records zero new duplicates. Code applied the v19 website-proof rules; reviewed identity rules governed the separate v20 merge.

Architectural limits

Six rows lack phones; one phone is shared by two differently named businesses. Phone is indexed but not unique, and the public table has no stable company identifier. Raw trade and locality labels need normalization. Detailed evidence is stored separately; complete row-level provenance is not established for every inherited record. A later revision should preserve frozen inputs, introduce stable company identities, retain disputed links and evidence, and reconcile accepted or uncertain search claims before any resubmission. Website presence and email presence do not establish current contact validity.

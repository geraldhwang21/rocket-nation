# Rocket Nation calling list: provenance and continuation

This guide identifies the exact v20 dataset displayed by website v0.9. The public repository includes its complete workbook and three browser data chunks. The local Rocket Nation `production/` record retains the frozen v19 input, the 100-record research input, the merge script, and the decision report. The private `geraldhwang21/rocket-nation-data` repository retains the earlier search receipts. A reader with only this public repository can inspect the final data, but cannot replay all private source captures.

## Reproduce v19 without new searches

Use a checkout with the **local Rocket Nation `production/` tree intact**. The public website repository alone is insufficient because it deliberately excludes the private raw responses and source captures. From `C:\Users\geral\dev\Rocket-Nation`, run:

```powershell
python production/verification/haiku-continuation-20261030/rebuild-v19-offline.py
```

The script checks the frozen v18 database hash, capture input hashes, page-body hashes, offline replay receipt and every preserved prior value. It rebuilds database and CSV in a temporary directory, checks the v19 database hash `2f57741a60199c05e5cde128a5e2ef8cf8c7e9dbfe71bd894f51b0c0d84abb9e` and CSV hash `f958ce4da7752bb99d16e4ed51f70cea0eb0cb32b3a4622b2fab70c3dc932064`, and removes the temporary files. It makes no network call and does not overwrite a deliverable. A successful run prints `exact_rebuild_passed: true`. If a dependency is missing or a hash differs, it fails; do not substitute a fresh network result or an older baseline. The rebuild script itself is retained in this permanent verification folder and copied into the private data repository with this guide. The final capture is about 1.4 GB and is retained locally in `production`; the private repository tracks the smaller provider receipts but does not contain every fetched page body.

This exactly rebuilds the **frozen v19 input to v20** from frozen v18 and retained v19 evidence. Fresh web searches cannot be expected to recreate the same responses, and deleted pre-v17 data cannot be reconstructed byte for byte. To audit the verification decision itself, inspect the retained `offline-publication-replay.json`, `inputs-manifest.json`, `results.jsonl`, page bodies, and `support/offline-replay.py`. The existing receipt records an enforced network-disabled replay; rerun that verifier only in the historical launcher layout because the `support/` copy has path assumptions from that layout.

## Reproduce the v20 union

With the frozen v19 CSV and retained 100-record input in the local Rocket Nation project, run `python production/verification/website-v09-revision5/build-v20.py`. The script verifies both input hashes before use, applies the reviewed identity rules, creates the 72,478-row CSV, SQLite database, and Excel workbook, and writes `pilot-merge-report.json` listing all 100 dispositions. It makes no network call. Rebuilding v20 never requires resubmitting a Serper or Haiku search. The code and report live in the local `production/verification/website-v09-revision5/` record. The source input was removed from the public site but retained in `production/inputs/website-pilot/`.

## Continue enrichment without repeating work

1. Start from the **v20** database and CSV hashes above. Preserve them unchanged; create a new numbered revision for any accepted additions. Do not resume from v17, the partial v18, the v18 successor, or v19 as if the 100-record reconciliation had not happened.
2. Build the next eligible queue by 10-digit phone after checking the current `calling_list` table and all durable claim records. Exclude existing nonblank websites and every phone with an accepted or uncertain Serper or Batch request, even if the search failed or yielded no website. The v19 manifest alone is a historical allowlist, not permission to resubmit it. Inspect `v18-serper-plan.json`, v18 claims and both v19 gate/lane intents and acceptance receipts before any paid call. A missing response after a recorded intent is uncertain until proven otherwise; use provider GET and receipt reconciliation first.
3. Maintain one coordinator for paid submissions. Partition any new queue into disjoint phone sets; persist immutable request payloads, intent markers and provider acceptance IDs *before* progressing. Never infer that a failed runner means its POST did not happen. The lane 12 recovery was allowed only because the raw failed-job stack showed the POST had not been reached, and it used an additional durable attempt marker.
4. Use the same proof rules for candidate websites: reject directories, social pages and private network destinations; fetch the page safely; require the phone visibly on the page and a company-name/domain match; retain the exact fetched bytes and their hash. A model statement or search snippet is not enough. Leave false, missing, blocked, malware, and ambiguous results unconfirmed. Preserve all original nonblank websites/emails and source precedence.
5. For each new scrape, start an empty dated capture; retain every parser input, response, cursor, cache, config and source hash; replay with network disabled; and compare the data hash before publication. Run row-count, nine-column, database-integrity, CSV-parity and no-loss checks. Phone uniqueness is no longer a valid invariant because of one preserved shared-phone conflict. Publish a new version only after these checks pass. Keep the captured evidence in `production`, not disposable scratch.
6. Do not reimport the 100-record research source. All 100 entries are accounted for in `pilot-merge-report.json`; 27 map to existing rows and 73 were added in v20. Review that report and the retained original before any later identity change.

# Rocket Nation calling list: provenance and continuation

This guide identifies the exact v19 dataset displayed by website v0.9. It is also the starting point for any later enrichment. The public website copy contains the final workbook; the private `geraldhwang21/rocket-nation-data` repository and the local `production/` record contain the frozen inputs and evidence. A reader with only the public website repository can inspect the delivered data and its hashes, but cannot replay private source captures.

## Reproduce the current result without new searches

Use a checkout with the **local Rocket Nation `production/` tree intact**. The public website repository alone is insufficient because it deliberately excludes the private raw responses and source captures. From `C:\Users\geral\dev\Rocket-Nation`, run:

```powershell
python production/verification/haiku-continuation-20261030/rebuild-v19-offline.py
```

The script checks the frozen v18 database hash, capture input hashes, page-body hashes, offline replay receipt and every preserved prior value. It rebuilds database and CSV in a temporary directory, checks both output hashes above, and removes the temporary files. It makes no network call and does not overwrite a deliverable. A successful run prints `exact_rebuild_passed: true`. If a dependency is missing or a hash differs, it fails; do not substitute a fresh network result or an older baseline. The rebuild script itself is retained in this permanent verification folder and copied into the private data repository with this guide. The final capture is about 1.4 GB and is retained locally in `production`; the private repository tracks the smaller provider receipts but does not contain every fetched page body.

This is an exact rebuild of the **current v19 output from frozen v18 plus retained v19 evidence**. It does not claim that fresh web searches can recreate the same responses, nor that the deleted pre-v17 data can be reconstructed byte for byte. To audit the verification decision itself, inspect the retained `offline-publication-replay.json`, `inputs-manifest.json`, `results.jsonl`, page bodies, and `support/offline-replay.py`. The existing receipt records an enforced network-disabled replay; rerun that verifier only in the historical launcher layout because the `support/` copy has path assumptions from that layout.

## Continue enrichment without repeating work

1. Start from the **v19** database and CSV hashes above. Preserve them unchanged; create a new numbered revision for any accepted additions. Do not resume from v17, the partial v18, or the v18 successor as if v19 had not happened.
2. Build the next eligible queue by 10-digit phone after checking the current `calling_list` table and all durable claim records. Exclude existing nonblank websites and every phone with an accepted or uncertain Serper or Batch request, even if the search failed or yielded no website. The v19 manifest alone is a historical allowlist, not permission to resubmit it. Inspect `v18-serper-plan.json`, v18 claims and both v19 gate/lane intents and acceptance receipts before any paid call. A missing response after a recorded intent is uncertain until proven otherwise; use provider GET and receipt reconciliation first.
3. Maintain one coordinator for paid submissions. Partition any new queue into disjoint phone sets; persist immutable request payloads, intent markers and provider acceptance IDs *before* progressing. Never infer that a failed runner means its POST did not happen. The lane 12 recovery was allowed only because the raw failed-job stack showed the POST had not been reached, and it used an additional durable attempt marker.
4. Use the same proof rules for candidate websites: reject directories, social pages and private network destinations; fetch the page safely; require the phone visibly on the page and a company-name/domain match; retain the exact fetched bytes and their hash. A model statement or search snippet is not enough. Leave false, missing, blocked, malware, and ambiguous results unconfirmed. Preserve all original nonblank websites/emails and source precedence.
5. For each new scrape, start an empty dated capture; retain every parser input, response, cursor, cache, config and source hash; replay with network disabled; and compare the data hash before publication. Run row-count, unique-phone, nine-column, database-integrity, CSV-parity and no-loss checks. Publish a new version only after these pass. Keep the captured evidence in `production`, not disposable scratch.
6. Treat the older 100-record website pilot as a separate candidate source. Its 25 phone matches can be cross-referenced; the remaining 75 require identity review before any import. Keep the pilot source and review record so later work can distinguish omitted records from verified duplicates.
